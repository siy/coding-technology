## Symmetry rule, widened to two axes

The user's ask was: *if a discipline exists in one path, it must be applied to the mirror path
or explained why not* — added to `jbct-reviewer` and, if needed, `jbct-coder`.

**Both agents already had a rule like this.** That changed the shape of the work entirely. The
existing rule covered only *parallel siblings* — the same operation across `Result`/`Option`/
`Promise`, overload families, parallel test suites. It said nothing about *inverse pairs*:
parse/render, decode/encode, import/export, read/write, acquire/release, subscribe/unsubscribe,
migration up/down. So `lift` records what it dropped and `emit` doesn't, and nothing goes red.

Adding a second near-identical rule beside the first would have created exactly the
inconsistent-application condition the rule exists to prevent — the existing rule's own scope
was an instance of the defect it describes. So it was **widened, not duplicated**: one
`### Symmetry Checks` section, two named axes, run both.

**Two guards keep it from becoming a noise generator:**

1. **Reviewer — a finding must name what breaks.** "Asymmetric" alone is not a finding. State
   the caller that cannot detect a failure, the invariant that holds one way only, the round
   trip that is not the identity. Some asymmetry is correct: a parser validates because its
   input is untrusted, while a writer may trust a model whose type already carries the
   guarantee. Correct asymmetry still needs a stated reason — missing reason is a Warning,
   missing discipline that breaks something is Critical.
2. **Coder — documenting is a complete answer; silence is not.** Explicitly *do not* build an
   unrequested partner or speculative reporting machinery. Told to "always mirror", the coder
   would generate code nobody asked for, colliding head-on with the minimum-code directive.
   The point is that the asymmetry is deliberate and legible, not that it is absent.

The verb split matters: **the reviewer detects, the coder avoids creating.** They cannot share
one wording.

## Two PFD fixes, wrong on PFD's own terms

Found while reviewing PFD's argument, not while applying any external frame — which matters,
because a fix justified from outside the book would be a retrofit and would not be worth making.
Both are wrong on the book's own terms. Neither is started.

**1. `foundations.md` overclaims the falsifier.** It says measuring backward on an existing
codebase works because *"the version-control history does not lie"* about how the system
actually changes. It does lie, in one specific and correctable way: **co-change is partly
endogenous.** Files change together partly *because the current decomposition forces them to*,
so raw co-change is downstream of the structure it is being used to falsify. A decomposition
that disagrees with history may be indicting the history.

The instrument survives with two qualifications, both formulation-level and neither requiring
tooling:

- **Measure cross-boundary co-change.** Coupling that crosses a boundary indicates
  misattribution whether the change was forced or induced.
- **Use restructuring events as natural experiments.** Co-change that survives a known
  restructure is real; co-change that vanishes was an artifact of the old structure.

This is a `Fixed` entry of the same shape the Rico exchange produced in 2.4.2 — the book's
argument gets stronger by getting narrower.

**2. The change-driver criterion is presented as general, while the Closing defines a scope
band.** The Closing already scopes PFD honestly (large, long-lived, multi-team backend), but the
decompose-by-change-driver criterion is stated without that scope attached. Domains exist where
the governing relation is not change — memory-access-driven designs, trust boundaries, and
concerns that co-change with everything. One sentence naming that closes the gap. The Closing's
own scope band probably already excludes all of them, which is why this is a wording fix rather
than a substantive one.

## Conventions confirmed

- **A verification's scope must match the claim's scope.** "Clean" means the repo, so the check
  means the repo. Anything narrower is a different, weaker statement and must be said that way.
- **Widen an existing rule; never add one beside it.** Two rules covering overlapping ground is
  the inconsistency the rule was written to catch.
- **Documenting an asymmetry is a complete answer.** Cheap enough to actually hold, which is the
  only property that makes a discipline stick.
- **Read the declaration, not the summary.** Specs, audits, summaries, and memory all encode
  errors that the source does not. This cost real work three times in one session.
- **Draft status decides the repo, not sensitivity.** Capture and unshipped drafts go to `../oss`
  or `../cdm`. `articles/` here is for work committed to shipping.
- **Prefer positive formulation to defensive.** A draft that pre-refuses objections nobody raised
  reads as weaker than one that states its position and links to the detail. The books carry the
  proofs; a short claim plus a link is enough. Stating an idea for discussion is not opening a
  fight, and writing as though it were makes it look like one.
- **Published work is history.** It stays as written, whatever the current rules say.
- **Private material stays private, including in handovers.** Path references here, nothing else,
  ever — and check the headings too, not just the prose.
