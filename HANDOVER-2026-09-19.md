## Read this first: four things that will bite a successor

**1. A SQUASH-MERGED COMMIT IS NOT AN ANCESTOR, AND GIT WILL TELL YOU IT IS UNMERGED.** The most
expensive error of the last session, and it is still live in this repo. I reported a runbook fix as
*done, committed, unmerged, no PR*; it had been squash-merged days earlier. `--is-ancestor`,
`branch --contains` and `branch --merged` all return false negatives **by construction** after a
squash, because the squash rewrites the commit. **Ask whether the CONTENT is present, or resolve the
PR: `gh api repos/<repo>/commits/<sha>/pulls`.**

**Its live instance:** `fix/deployed-site-headers` is **provably merged** — that commit resolves to
**PR #78, merged 2026-09-12** — but `git branch -d` refuses it, inheriting the same false negative.
Deleting it needs `-D`, which the standing rule forbids. **That rule's safety property has a blind
spot under squash-merge**, and this branch is the worked example. Left in place deliberately; it is
the owner's call, not a thing to quietly `-D`.

**And the tag half, which generalises.** The bad claim rode into a greppable `[verified:]` namespace
citing `git ls-remote` — an instrument that can establish a branch and its SHA and **cannot, even in
principle, establish "has no PR"**. Half the claim was checked; the other half inherited its
credibility. **A tag must cite evidence that can bear every claim it sits on.**

**2. The retention rule has now fired twice and is self-sustaining.** Root keeps the current handover
and its immediate predecessor. `09-09` moved on 2026-09-17; **`09-12` moves with this one.** The next
handover moves `09-17`. Expect to do that move, not discover it.

**3. You do not commit in the private record — the `oss` session does.** `(private path)`:
*"Committing is not the writing agent's job. Agents drop files here and move on; the agent working in
`oss` commits and pushes them."* Project memory used to say the opposite and has been corrected.
**Drop files and stop.** Verified working this session: nine dropped paths were swept, committed and
pushed by that session, and confirmed present in `HEAD` by content — because an empty `git status`
is equally consistent with *committed* and with *lost*.

**4. Presence is not agreement.** A rule can be "homed" in a document that also contradicts it. When
checking whether something is recorded, check that the home **agrees**, not that it mentions the
subject.

## The Aether runbook skill — decided how, not whether

**Owner ruling 2026-09-15: the runbook-skill proposal and the manual-tester board item are decided
together.** It scopes **HOW** the decision is made, **not WHETHER to build.** The underlying decision
is still open; a reader who takes "decided together" as approval has misread it. The proposal lives in
the private record and carries `[verified:]`/`[unverified:]` tags in one namespace so a single sweep
returns both.

**The finding that shrank it: most guardrails already exist.** Per-operation authorization (#299,
VIEWER/OPERATOR/ADMIN, deny-by-default for unlisted routes); role-scoped API keys with
`DEFAULT_ROLE = "VIEWER"`; CLI key create/list/revoke/rotate; dry-run on the declarative path only.
So the skill binds its modes to existing roles rather than building new ones.

**The real gap is credential delivery, not authorization:** keys arrive via the `AETHER_API_KEYS`
**environment variable** — the ambient-credential pattern `with-hcloud` exists to eliminate. Settled
design points: skill and runbooks bundle into the CLI; the credential wrapper must be an
**executable on PATH**, not a shell function; **a refused capability must not produce the same
message as an uninstalled tool**; escalation impossible, de-escalation mandatory.

**Owed by the CTO, with its condition:** a `know:` commit recording the ruling, after rc4's merge
round completes and the tip is green, before the candidate tag moves. `know:` commits live in
`pragmatica`, which this session does not edit — **so a read point taken there will not see this
ruling until that commit exists.**
