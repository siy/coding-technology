## Run 1 — three corrections, and where it actually stands

**This is the item most likely to be misread from a summary, so read the whole section.**

**Run 1** (8 implementers) leaked: two treatment agents read the Pragmatica source and one iterated
against `jbct lint` to zero findings. Clean arm n=2. **P1 not evaluable.** The cause was mine — JBCT
needs an external library whose signatures matter for compilation, idiomatic Java needs nothing outside
the JDK, so only the treatment arm had a reason to leave.

**Run 1b** (10 implementers) fixed isolation by vendoring the signature appendix into the prompt.
**All ten disclosed `READ_OUTSIDE_PROMPT: no`.** Result: treatment shape convergence 77.66 against
control 77.71 — margin **−0.05**. Published as "determinism falsified".

**Then the author dismantled the metric, correctly, in two moves:**

1. *Leaves and routing are determined by the process — how can implementations differ?* Inspection
   confirmed it: **all five treatment implementations have the same skeleton** — parse → fork-join over
   three independent lookups → guards → persist → best-effort confirm.
2. *A Leaf is atomic by definition.* Therefore a 45-vs-25 "LEAF" spread cannot be a difference in
   Leaves. It isn't: `shape-census`'s LEAF bucket means *any method that does not compose*, which
   includes `message()`, `masked()`, `normalized()`, `isWellFormed()`, and failure factories. t1 wrote
   **14 named failure factories**; t4 wrote **five `message()` overrides**. That one stylistic choice
   accounts for most of the gap.

**So P1 measured error-construction style, not structure.** A second defect compounds it: scoring the
use-case file alone gives the control **100.00 convergence with sd 0.0** — because every control
use-case file is 100% UNCLASSIFIED. The control can score perfect agreement *by being uniformly
unclassifiable*. The metric measures agreement in a vocabulary only one arm speaks.

**Current standing: determinism is neither supported nor falsified. The instrument was wrong.**
The "falsified" headline in `CONVERGENCE-RERUN-RESULTS.md` is unsafe and needs a third correction
written into it.

**What survives all of it:** distinctiveness. SEQUENCER 5.0-20.5% against a flat 0.0%, UNCLASSIFIED
0.0-1.7% against 19.2-42.3% — total separation, both runs, and these are *between-arm* differences that
the metric's flaw does not touch.

**Run 1c, agreed with the author:** compare **data dependency graphs**, not method histograms — the
ordered set of external calls, which are joined versus chained, where guards sit, which failure is
absorbed. The book already names the DDG and its three operators. **The ten implementations are already
on disk**; no new agents needed.

## The error-construction gap (open, under discussion)

Fell out of the Run 1 forensics and is a genuine book defect.

`error-handling.md:97` — the canonical "Defining Typed Errors" example — **teaches hand-written prose in
`message()`**, in two styles in one code block. `Cause.message()` is abstract in Pragmatica, so every
failure type is *forced* to supply one. Three incompatible styles appeared in the wild: named factories
(t1), `message()` overrides (t4), enum-with-field (`jbct-loan`).

**The author's position: prose in `message()` is an antipattern.** Reasons, sharpened: a rendering
concern in a domain type; duplicates the record's data as prose so the two drift; invites string-matching
in tests, which the 4.7.0 mutation caution explicitly warns against; and redaction must be repeated per
message (three implementations independently masked `TaxId`).

**Proposed fix, not yet ruled on:**

- *Mechanism* — either a `default String message() { return toString(); }` on Pragmatica's `Cause`, or
  a JBCT-side `interface DomainCause extends Cause` carrying that default. Records then render
  themselves, always in sync, with redaction controlled once in the value object's `toString()`.
- *Rule* — record when it carries data, enum constant when it does not; never hand-write prose;
  user-facing text produced at the boundary by an exhaustive switch (which finally *uses* the
  exhaustiveness the book already sells); tests match on type, not string.

**The open question that decides the size of this:** where is the line between a typed failure and a
cheap `Causes.cause("Age 0-150")`? The book uses bare string causes freely for value-object validation.
Proposed line — *whether a caller can act differently on it* — but this needs the author's ruling.

Two smaller ones: should the default compose with `source()` for wrapped causes, and is an enum
constant's derived message just its name?

It merges what were two disconnected pieces — a `jbct-loan` parent repo holding `SPECIFICATION.md` and
the Spring arm in one commit, and `jbct-slice/` as an untracked nested repo with 56 commits of its own.
Grafted with `git subtree`, so the slice's history survives as ancestors rather than a flattened
snapshot.

**CI covers the Spring arm only, and the reason is a publication gap.** The slice pins
Pragmatica/Aether `1.0.0-rc3`, and `aether/resource-api` and `aether/resource-http` are **not on Maven
Central at any `1.0.0` version** — rc2 does not rescue it either. A clean runner cannot resolve them, so
the slice job would fail on dependency resolution rather than on anything about the code. The workflow
carries the job commented out with the coordinates named. This is the third time this gap has bitten:
it is also why the slice did not compile at `0.17.0`. **Publishing those two artifacts unblocks it.**

**Parity was audited, not assumed** — and each arm had got different things right:

| | JBCT slice | Spring Boot |
|---|---|---|

| Loan reaches `PAID_OFF` | already correct | fixed |
| Non-positive payment rejected | already correct | fixed (400; was hitting the 500 catch-all) |
| Missing loan → 404 | fixed | already correct |
| Outage vs business rejection | fixed (503) | fixed (was 422 — "your request is unprocessable" while KYC was down) |

**Test counts are not comparable and the README says so.** Value-object-per-concept generates unit

discharged, not the same totals.
