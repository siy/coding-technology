## Durable decisions / principles established this session

1. **"Growing context"** = the canonical name for the knowledge-accreting pipeline pattern, in **both** books. JBCT: *stage records* are the mechanism. PFD: it's the design-level discipline.
2. **Shared name, altitude-appropriate register.** Concept *names* stay identical across PFD↔JBCT to prevent the misunderstanding "growing context" had become; the *language* around them tracks each book's level — PFD abstract/language-neutral, JBCT technical/mechanism. Uniform language would be the error.
3. **The defensive-residue filter** (a reusable review lens): cut text that defends against, reassures about, or warns of a mistake a fresh reader has no context for — usually it's the book arguing with its own earlier draft. The positive sentences survive; the defensive ones are residue. (Caught the refrain, the footers, and the §194 tail this session.)
4. **Positioning of the unified runtime / Aether**: it *dissolves the modulith-vs-microservices dilemma* (deploy one or many without rewrite); microservices stays a legitimate horn with a named cost. The event-driven-microservices critique is stated as **derived contrast** in the existing §82 self-defeating-combinations list, never as an attack and with no camp named. **Deployment topology = the operating-cost axis** (the framing that earns the cluster its weight).
5. **JBCT build now requires the Noto Emoji font** for monochrome emoji rendering under xelatex.

## Teed up but NOT written — the state-management article

A standalone article (dev.to/Medium via the article-cross-poster), **orthogonal to JBCT, not for either book's PDF**. Spine, agreed with the author:

- **Thesis:** a function call *is* a message exchange (CPS makes it exact: the return value becomes an argument passed forward). In-flight data — call parameters, return values, events — *is* state, transient state. Functional composition and EDA are the **same computation** differing only in the **durability** of that in-flight state.
- **The continuum:** stack frame → continuation/promise → queue → store. Sync composition is the stack tier, async pipeline the continuation tier, EDA the queue tier, persistence the store tier. The DB is just the most durable tier; eventual consistency is the gap between async stages, made long enough to notice. `combine()` (Kotlin Flow) is the small-resident corner where held state and in-flight messages coincide.
- **Not push/pull.** That's a *different* axis (Iterable/Observable, Meijer) — one sentence to set it aside so readers don't conflate.
- The **book got the backend kernel** (the durability reframe at the composition-substrate axis); the article is the cross-paradigm generalization. Entry point: open on the `combine()` "where does this show up?" question, earn the duality mid-way, payoff = "it was always state management."

## Conventions in force (UPDATED this session — note the two corrections)

- **CHANGED — no thread footers.** The per-chapter `*Threads advanced: …*` foot tags were **removed** from PFD. Do **not** re-add them; the coverage map lives in `book-pfd-meta/` for the author only. (Vignette/italic at chapter top still stands.)
- **CHANGED — no "non-functional".** The book uses **"system qualities"** (system level) and, at detail, the four categories: **SLO** (service-level objective, now spelled out), **constraint**, **operational target**, **substrate-shaping**. "non-functional"/"NFR" no longer appears anywhere, including the former deliberate naming-to-refuse — that exception is **gone**.
- **Em-dash ≤2 per prose paragraph** (definition lists / table cells exempt). Verified across all edits.
- **Shared name, altitude-appropriate register** (see Durable Decisions #2). **"Growing context"** is the shared name.
- **Product names:** none except **Aether** (where the slice/unified-runtime deployment mode is load-bearing) and positive crediting (Jackson, King, Loth, Yevtushenko, Poltorak, Fritzsche).
- **Register:** sharp, positive, research-cited — **no competitor/microservices/SOLID teardown.** Cost is stated as honest accounting (the operating-cost framing), never as attack; combinations that defeat themselves are surfaced as **contrast**, no camp named.
- **Code:** pseudo-code for type shapes, Java for composition; JBCT idioms strict (single-param `Result<T>`, `Promise<T>` carries failure — no `Promise<Result<T>>`, `Unit` not `Void`, `TypeName.typeName(...)` factories, method references, sealed `Cause`). Use cases/workflows are plain interfaces with explicit `apply`.
- **Cohesion vocabulary:** the change-driver test has two directions — **completeness** (all the driver governs) and **purity** (only what it governs). Both required.
