## Done this session (2026-10-14..16, verified)

**PR #100 merged (`4e59a5b`)** — Fork-Join `all`/`any` settled across both books, site, skill, agents, training.
- **`Promise.all` is not fail-fast.** It waits for every input and accumulates all failures into a `CompositeCause`
  (via `Result.all`); `allOrCancel`/`allOfOrCancel` are fail-fast. Probe on core rc3 + rc4 jars: two inputs failing
  at 50 ms + one succeeding at 800 ms -> `all` ~827 ms with both causes, `allOrCancel` ~52 ms with the first.
- **Owner rule (2026-10-15): prefer `all()`.** `allOrCancel()` only when the caller must hear about a failure before
  the slowest input could finish and the first failure decides. **It saves waiting, not work**: `cancel()` is
  `fail(PROMISE_CANCELLED)`; a 300 ms input completed after `allOrCancel` returned (probed). In book, skill,
  `jbct-coder`, `jbct-reviewer` (new search row).
- **A single failure in a join also arrives as a `CompositeCause`.**
- **`any()` is a Fork-Join case in two separate forms** (owner ruling 2026-10-14, same as oss recipe proposal rev 4):
  `Promise.any` = race (first success, rest cancelled); `Result.any`/`Option.any` = ordered fallback (synchronous,
  lazy `Supplier` overloads; the owner: no simple way to make them parallel, sequential is expected). No `anyOf`.
- Collateral fixes found by the independent verifier: the skill's timeout aspect never timed out (used
  `Promise.any` + nonexistent `Promise.promise(timeout)`; now `operation.timeout(timeout)`); `TimeSpan.seconds(5)`
  does not exist (`TimeSpan.timeSpan(5).seconds()`); Appendix A `Result.any` signature; site glossary; Fork-Join
  diagram's "First Error"; arity is 1-15.
- Probes: session scratchpad (temporary — assume gone). Run them with the core jar plus `slf4j-api` on the classpath.
