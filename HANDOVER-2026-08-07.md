## JBCT 4.4.0 — the testing pass

Produced by implementing the book's own testing advice against real code and finding where
it stopped giving answers. Two of the six changes were **defects**:

- **No worked example contained an adapter contract test**, though the book prescribes them
  — leaving every stub in every example an unverified boundary assumption. `InventoryChecker`
  now has one, with the exception-to-typed-failure translation as the load-bearing case.
- **`PriceCalculator` was declared in Step 5 and never implemented**, while *Testing in
  Practice* named `PricingEngine` as its complex-leaf illustration and never worked one.

The rest: decision-space counting *alongside* the branch heuristic (which **stays** — it
predicted 7 of 7 isolate-or-not decisions correctly in `jbct-loan`), "100% coverage" retired
as the value-object target, and the two rules the worked examples had been following
silently (interaction assertions only where the effect is invisible; one composition test
for propagation plus N cheap vectors).

Counting the decision space found something unplanned: **three of `PriceCalculator`'s
eighteen combinations are structurally impossible** — an order over the large-order
threshold, discounted by at most 10%, always clears free shipping. Counting tells you which
cells cannot occur, which no branch count reports.

## Two mistakes, both the same shape

**I trusted documentation over the tool, twice.**

1. **The `/release` skill said `./build-pdf.sh --final` for JBCT.** It does not take a flag —
   it takes an optional *output name*, so `--final` became the filename and the build died on
   `rm -f --final-content.pdf`. I had written that flag into the skill three days earlier by
   generalizing from the PFD/AS/Aether scripts without opening JBCT's usage header.
2. **The cross-poster skill documented `~/.config/article-cross-poster/`.** The real path is
   platform-native: `~/Library/Application Support/article-cross-poster/config.toml`. I
   checked the documented path, found nothing, and reported the tool as unconfigured. It was
   configured all along.

Both docs are fixed, both now say to ask the tool. The rule worth carrying: **when a tool can
report its own state, ask it** — `config path`, `config show`, `--dry-run`, `--help` all
existed and cost nothing.

## Publishing knowledge now recorded (was only in-session)

In `reference_publishing.md`:

- Config path is platform-native, **not** XDG. Ask `config path`.
- **Medium `contentFormat` defaults to `markdown`, which does not render tables.** Either
  convert them or pass `--format html`. **Six drafted articles still contain tables** —
  `--format html` is the cheap route and means they do not need rewriting.
- `--clean-ai` converts em dashes to `--`. That is *why* every article uses `--`; the
  convention is mechanical, not stylistic.
- `published:` is a dev.to **publish-on-push directive**, not a status. Defaults to `true`.
- Verify with `post -t devto,medium --dry-run <file>` before posting.
