## The edge list

- **Monolith → Mesh of self-managed Shards** (deployment: single→multiple, replicated @ whole system) — feasibility: data must split into semi-independent parts, or shards need a mesh engine to intercommunicate | costs: mesh-engine complexity, slow/corrupting intershard transactions, clients must know their shard | reversible: not addressed | decomposable: yes — sharding-proxy variant below is the lower-coupling first step | src: "Evolutions of a Monolith that lead to Shards"
- **Monolith → Shards behind a Sharding Proxy** (deployment: single→multiple @ whole system) — feasibility: data must be sliceable into independent, self-sufficient parts (no cross-shard traffic) | costs: proxy is a single point of failure and adds latency unless replicated/co-located | decomposable: this *is* the lower-cost decomposition of the mesh edge above | src: same page
- **Monolith → stateless Pool + Load Balancer + Shared DB** (deployment: single→multiple @ whole system; persistence unchanged, now explicit) — feasibility: persistent data must stay a manageable size | costs: DB becomes the throughput ceiling and a single point of failure; LB adds latency | decomposable: cheapest scaling step Poltorak lists — defers the real constraint (the DB) rather than resolving it | src: same page
- **Monolith → Layers (structural split, no deployment change)** (composition/structure @ whole system — *not* a topology move) — feasibility: a natural high-level/low-level seam must exist | costs: one-time restructuring effort, small performance penalty | reversible: yes, named — "Merge several layers" below | decomposable: this is itself the decomposition step for later Services/Sandwich/BFF splits | src: "Evolutions of a Monolith that result in Layers"
- **Monolith → Layers + dedicated database** (persistence: implicit→single shared, explicit @ whole system) — feasibility: system needs to query/edit a large data volume | costs: DB fine-tuning burden, vendor lock-in, most DBs don't scale on their own | decomposable: explicit staged "further steps" list (LB → Layers split → Polyglot Persistence → CQRS → Space-Based) | src: same page
- **Layers → Sandwich (domain layer only split into Services)** (deployment: single→hybrid @ one layer, not whole system) — feasibility: low-level business logic must comprise loosely coupled subdomains | costs: future domain-structure changes get harder, system-wide use cases harder to debug, performance degrades once distributed | reversible: yes, named — "merge all domain-level services back" | src: "Evolutions of Layers that help large projects"
- **Layers/Shared-DB → Event-Driven Pipeline** (composition substrate: direct→event-based @ whole system) — feasibility: use cases must already be trivial sequences of loosely-coupled, coarse-grained steps | costs: whole-system debugging gets hard, latency rises, component/pipeline count can explode | decomposable: yes, explicit chain — add Middleware → split shared DB by subdomain → Space-Based scaling → extract Orchestrator | src: same page
- **Choreographed Services → Orchestrated Services** (composition substrate: choreographed→hub-orchestrated @ whole system) — feasibility: use cases must decompose into sequences of high-level steps | costs: message count roughly doubles, orchestrator becomes a new single point of failure, couples the services' qualities to it | reversible: yes, named in the reverse direction (below) | src: "Evolutions of Services that add layers" / "Evolutions of a Pipeline"
- **Orchestrator → subdivided into Layered Services** (deployment/composition: single hub→distributed-by-subdomain @ whole system) — feasibility: orchestration logic must already be weakly coupled between subdomains | costs: loses the single client-facing team, service teams become mutually interdependent, no shared view across all scenarios | reversible: this *is* the documented reverse of the prior edge — round-trip is real but each direction has a different cost shape, not a clean undo | src: "Evolutions of an Orchestrator"
- **Shared DB → Sharded DB** (persistence: single shared→sharded shared @ whole system) — feasibility: data must be independent, shardable records | costs: cross-shard joins/aggregates disappear — that logic moves into the services, a capability loss, not just an inconvenience; many DB instances to manage | src: "Evolutions of a Shared Repository"
- **Shared/Sharded DB → Space-Based Architecture** (persistence: shared/sharded→distributed in-memory mesh; state effectively cached current-state @ whole system) — feasibility: **data collisions must already be acceptable** — a consistency downgrade pre-authorized before the edge is on the table, not discovered mid-migration | costs: continuous, not one-time — "high operational cost because the nodes exchange huge amounts of data," scaling with node count; no analytical queries; low latency only while the dataset fits one node's memory | src: same page (recurs under Shards and Layers-performance)
- **Shared DB → per-service private DB (Polyglot / Layered Services)** (persistence: single shared→per-component/polyglot @ whole system) — feasibility: domain data must be weakly coupled | costs: cross-subdomain joins gone, data duplication/transfer cost, multiple DBs to administer | decomposable: yes — "further step" points at CQRS Views/Query Service to patch the lost joins | src: same page
- **Services → merged back into Monolith or Layers** (deployment: multiple→single @ whole system) — feasibility: services must already use compatible technologies | costs: teams become interdependent again, loses per-subdomain quality variation and granular scaling, "if anything fails, everything fails" | reversible: this is itself the named reverse of the Monolith→Services edge, framed as corrective (paying to undo a split that no longer fits changed domain knowledge), not cyclical by default | src: "Evolutions of Services that restructure services"
- **Layers → merged back into Monolith/3-tier (performance move)** (deployment: multiple/layered→single @ whole system) — feasibility: development must be effectively finished, no further change expected | costs: **explicit ratchet warning** — "the code is frozen, it will be much harder to evolve," teams lose independent work | reversible: stated as a deliberate one-way trade (freeze mobility to buy ~5% performance) | src: "Evolutions of Layers to improve performance"
- **Add an infrastructure layer — Middleware / Shared Repository / Proxy (each materializes a shared coordination, persistence, or boundary layer)** (composition substrate and/or persistence gain a shared layer @ whole system) — feasibility: services need uniform scaling/recovery (Middleware), a data volume outgrowing files (Shared Repository), or external clients to mediate (Proxy) | costs: latency and a new single point of failure per added layer, admin overhead, stacking repeats the cost | reversible: **all three are stated as practical one-way ratchets**, the same claim made three times independently — "A Middleware is unlikely to be removed … once it is built into a system"; "Once a database appears, it is unlikely to go away"; "It usually makes little sense to get rid of a Proxy once it is integrated" | src: "Evolutions of a Middleware" / "…Shared Repository" / "…Proxy"

## Mapping notes (honest mismatches)

1. **Metapatterns bundle axis moves; our edges want them unbundled.** Poltorak's unit is a named shape (Shards, Sandwich, Space-Based Architecture) that typically fixes 2–3 of our axes at once under one Prerequisite/Cons block. Some evolutions are clean single-axis deltas in our terms ("Shard the database" moves only persistence configuration); others — "Divide the domain layer into Services" — move deployment topology *and* composition substrate together as one atomic step. Where the chapter wants sequenced single-axis deltas, his catalog has to be split further, not just relabeled.
2. **His prerequisites gate the destination, not the crossing.** "The data can be split into semi-independent parts" is a fact about the target shape's fitness for the domain, not about whether the system stays operable *while* the split is in progress. Our "intermediate-state feasibility" concept has almost no direct counterpart in his Prerequisite fields — one entry gestures at it (Front Controller tracks in-flight request status), but this is the biggest structural gap for a migration-as-pathfinding chapter to fill in its own voice.
3. **His Cons lists conflate three cost types our model separates.** One bullet list mixes durable always-on costs ("nodes exchange huge amounts of data"), one-time optionality costs ("future changes to domain structure will be hard" — an irreversibility cost), and plain new failure modes ("the Orchestrator may become a single point of failure"). Sorting each bullet into failure-mode-amplification vs. always-on-cost vs. irreversibility-cost is a judgment call per bullet, reflected in the annotations above.
4. **Reversibility is never a stated field.** It has to be inferred either from a named reverse evolution elsewhere in the appendix (Layers↔Monolith, Services↔Monolith, Sandwich↔Layers, Orchestrator↔Layered-Services all have both directions documented, with *different* cost profiles per direction — not a symmetric undo) or from prose "ratchet" asides (Middleware/Shared Repository/Proxy). The ratchets corroborate this book's F6 (irreversibility orders commitment) empirically, without deriving it structurally.

## Coverage note

Dense: **deployment topology** (the spine of the appendix — Monolith/Shards/Services/Pipeline are deployment-defining shapes), **composition substrate** (direct vs. choreographed vs. orchestrated vs. event-based recurs across Middleware, Orchestrator, and Pipeline evolutions), **persistence configuration** (the Shared Repository page is entirely this axis: sharded, Space-Based, per-service, polyglot).

Thin: **read/write model** — CQRS is named repeatedly only inside "Further steps" pointers, never given its own Prerequisite/Cons entry. **State storage** (current-state vs. event-sourced) — Event-Driven Architecture appears as a composition-substrate choice, not a storage-model transition in its own right.

Absent: **recovery class** (BER/FER/design-out). Middleware-level fault tolerance — restart, replication — is covered repeatedly; the business-semantics choice this book's recovery axis names (compensate vs. continue-degraded vs. redesign-to-avoid) doesn't appear anywhere across the 18 pages reviewed. Ch. 10 needs its own worked examples for recovery-class transitions, same as the pathfinding draft already does with BER (payroll merge-back).
